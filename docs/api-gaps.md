# Saga API – Gaps & Improvement Suggestions

> Audience: Maintainers of **saga-core** (`C:\Projekte\saga-core`).
> Purpose: This document lists features that the Saga UI requires or that would
> improve it, which are currently **not** covered by the REST API. For each item:
> impact, urgency, and a concrete implementation proposal.

Examined API surface (REST, port 8000, Bearer auth): `GET /health`,
`POST/GET /documents`, `GET /documents/{id}`, `GET /documents/{id}/status`,
`GET /documents/{id}/file`, `PUT/DELETE /documents/{id}`, `POST /search`,
`GET /categories/tree`, `GET /categories/{path}/documents`, `GET /export/documents`.

---

## Gap 1 – Missing CORS Headers (relevant only for direct browser access) · low

**Finding:** The REST app (`src/saga/api/app.py`) does not register a
`CORSMiddleware`. A browser frontend from a different origin could not call the API
directly.

**Impact on the UI:** **None**, as long as the UI uses the chosen **BFF proxy pattern**
(server-to-server calls do not require CORS). This only becomes relevant if the UI is
later configured to call Saga directly from the browser.

**Suggestion (optional, disableable):** Make CORS configurable.

```python
# in create_app(), after app = FastAPI(...)
from fastapi.middleware.cors import CORSMiddleware

if cfg.api.cors_allow_origins:
    app.add_middleware(
        CORSMiddleware,
        allow_origins=cfg.api.cors_allow_origins,   # e.g. ["https://ui.example.com"]
        allow_credentials=True,
        allow_methods=["*"],
        allow_headers=["*"],
    )
```

Add a `cors_allow_origins: list[str] = []` field to `ApiConfig` (core/config.py) and
expose it in `config.yaml`. Empty default = unchanged behaviour.

## Gap 2 – No Document / Title / Metadata Filter Search · medium (optional v1)

**Finding:** `GET /documents` only supports `page`/`page_size` (no full-text, title, or
metadata filters, no sorting). `POST /search` returns **semantic chunk snippets**, not
"find document by filename/title".

**Impact on the UI:** UI v1 uses hybrid search and category browsing and can work without
this. However, a classic "filter by filename/title" is not possible.

**Suggestion (optional):** Extend `GET /documents` with filters, e.g.:
- `q` (substring match on `title` via OpenSearch),
- `doc_type` (exact filter),
- `status` (e.g. only `ready`),
- `sort` (`created_at`/`updated_at`/`title`, asc/desc).

Example signature in `routes/documents.py`:

```python
async def list_documents(
    services: ServicesDep,
    page: int = 1,
    page_size: int = 0,
    q: str | None = None,            # title substring
    doc_type: str | None = None,     # exact type
    status: DocumentStatus | None = None,
    sort: str = "created_at:desc",
) -> DocumentListResponse: ...
```

Implement server-side in `OpenSearchStore.list_documents` as additional `bool`-query /
`sort` clauses. Fully backwards-compatible (all parameters optional).

## Gap 3 – No Manual Re-categorisation / Move / Rename · low (out of scope for v1)

**Finding:** Categories (`category_paths`, `folder_structure`) are generated by the LLM
during ingestion and are **read-only** via the API. There is no endpoint to change the
category or title of an existing document (only `PUT` = replace file, which triggers
re-analysis).

**Impact on the UI:** The tree is a **read-only view**; drag-and-drop moving is not
possible. Accepted for v1 (out of scope, see
[`requirements/01-functional-requirements.md`](requirements/01-functional-requirements.md)).

**Suggestion (future, if desired):** `PATCH /documents/{id}` to update individual
metadata fields (`title`, `folder_structure`, `category_paths`, `doc_type`,
`extracted_values`) **without** re-conversion. Validate paths and re-index only the
affected document fields (chunks remain untouched if only document metadata changes).

## Gap 4 – Content-Disposition at `/file` for Inline Preview · low

**Finding:** `GET /documents/{id}/file` always sets
`Content-Disposition: attachment; filename="..."`. For **inline** preview (PDF, image)
in the browser, `attachment` is suboptimal (forces download semantics).

**Impact on the UI:** **No hard blocker** – the BFF can rewrite the header to `inline`
when serving the preview. A proper option in the store would be cleaner.

**Suggestion (optional):** Add a query parameter `disposition=inline|attachment`
(default `attachment` = unchanged):

```python
@router.get("/{document_id}/file")
async def download_document_file(services, document_id, disposition: str = "attachment"):
    ...
    return Response(content=data, media_type=document.mime_type or "application/octet-stream",
        headers={"Content-Disposition": f'{disposition}; filename="{document.title}"'})
```

Workaround in the UI (without store changes): the BFF rewrites the Disposition header
when proxying, depending on whether a preview or download is requested.

---

## Gap 5 – No Bulk / Aggregate Endpoint for Dashboard Metrics · very low

**Finding:** For an overview (e.g. "X documents, Y processing, Z failed") there is no
aggregate endpoint.

**Impact on the UI:** Minor. The UI can use `GET /documents` (total) and
`GET /categories/tree`; status counts would be expensive without an aggregate.

**Suggestion (optional, nice-to-have):** `GET /stats` returning
`{ total, by_status, by_doc_type }` based on OpenSearch aggregations.

---

## Summary / Prioritisation

| # | Topic | Required for UI v1? | Recommendation |
|---|-------|---------------------|----------------|
| 1 | CORS | No (BFF) | Optional, disableable |
| 2 | Title / metadata search | No | Optional, useful later |
| 3 | Re-categorisation / rename | No | Future feature |
| 4 | `inline` disposition at `/file` | No (BFF workaround) | Optional, cleaner |
| 5 | Stats aggregate | No | Nice-to-have |

**Conclusion:** UI v1 is **fully implementable with the existing API** (thanks to the BFF
proxy). None of the gaps are blockers. Items 1, 2 and 4 are the most worthwhile optional
improvements for Saga.
